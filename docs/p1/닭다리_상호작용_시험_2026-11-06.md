# 닭다리 상호작용 시험 — XR 시뮬레이터

> 후속: 같은 절차를 고래밥과 포테토칩에 적용했고, 프로젝트 색공간 문제를 찾아 **Linear로 바꾼 상태에서** 이 문서의 증거를 다시 찍었다. [상품 제작 과정 시험](상품_제작과정_시험_2026-11-07.md) 참조. 이전 Gamma 상태의 닭다리 Unity 화면은 실제보다 어둡다.

## 결론

**시뮬레이터에서 작업대 배치 → 집기 → 회전 → 스캔 판정 → 놓기 → 다시 집기 → 바닥 낙하 복귀 흐름이 끝까지 동작한다.** 에디터 Play 모드와 Windows IL2CPP Development 플레이어에서 각각 48개 검사를 모두 통과했다(실패 0, 종료 코드 0).

이것은 **시뮬레이터 검증**이다. Quest 2, 실제 컨트롤러, 손맛, 멀미, VR 성능은 확인하지 않았다. 크기·무게는 임시값이고, 밑면에는 결함이 눈에 보이게 남아 있다. 상호작용 개발에는 쓸 수 있지만 **최종 품질 상품은 아니다.**

| 구분 | 상태 |
|---|---|
| 자동 검사 통과 | 에디터·IL2CPP 플레이어 각 48/48 |
| 눈으로 확인 | 렌더, 글자 방향, 프록시 맞춤, 회전 시 각 면 |
| 호출만 하고 결과 미확인 | 햅틱(0.3/0.05초, 0.6/0.1초), 스캐너 소리 |
| 미검증 | HMD, 실제 OpenXR, 컨트롤러 조작감, 양안 렌더, 72fps, 실제 바코드 이미지 판독 |
| 미확보 | 실측 크기·무게, 밑면, 가격 |

## 검증 내용

입력은 **가상 키보드·마우스 → XR Device Simulator → 시뮬레이션 컨트롤러 → XRI 입력 액션 → NearFarInteractor** 경로만 쓴다. 검증 코드는 상품을 직접 옮기거나 인터랙션 매니저를 호출하지 않고 상태만 읽는다. 이전의 W 이동 검증과 별개로, 이번에 처음 집기 자체를 검증했다.

정지 상태의 손-상품 오차가 0.0000m인 것은 Velocity Tracking이 물리 스텝마다 목표까지 속도를 다시 계산하기 때문이다. 물리를 거치지 않은 결과가 아니라는 점은 `movementType=VelocityTracking`, `isKinematic=false`, 작업대에 막히는 시험으로 따로 확인했다.

## 구현

프리팹은 구현 문서 4.3절의 4겹 계약을 따른다.

```text
P_dev_dakdari_01   (+1 스케일, 레이어 Interactable)
│   Rigidbody · BoxCollider(프록시) · XRGrabInteractable · ProductPrefab
├─ Splat           (레이어 Splat) GaussianSplatRenderer, localScale=(-0.29329, 0.29329, 0.29329)
└─ BarcodeTrigger  (레이어 BarcodeFace, 태그 Barcode) 끝면 안쪽 2cm 두께 트리거
Assets/Data/SO/dev_dakdari_01.asset   ProductData (SizeIsMeasured=false)
```

**음수 스케일 처리.** 기존 씬의 X 반전을 없애면 글자가 거울상이 된다. 그래서 반전은 유지하되 시각 자식 `Splat`에만 두고, 물리를 담당하는 루트는 +1 스케일로 둔다. 자식에는 충돌체가 없어 물리와 집기에 영향을 주지 않는다. 회전한 상태에서도 글자가 정상임을 화면으로 확인했다. 스플랫 렌더러는 공분산과 SH 시선 방향을 물체 행렬로 계산하므로 반전을 포함해도 수식상 맞다.

**상품 중심과 축.** `scripts/windows/fit_product_box.py`가 PLY에서 상자를 추정한다. 불투명도 0.3 이상인 42,569개 점의 축별 1~99 백분위 상자이고, 처음 PCA 축에서 부피가 최소가 되도록 10.1° 보정했다. 앞면(+Z)과 윗면(+Y)은 6방향 검토 화면을 보고 사람이 정했다. [맞춤 기록](../../Assets/Data/Provisional/dev_dakdari_01.box_fit.json).

**임시 값.** 상품별 [`Assets/Data/Provisional/dev_dakdari_01.json`](../../Assets/Data/Provisional/dev_dakdari_01.json)에 모았고 `Data/products.csv`에는 넣지 않았다.

| 값 | 현재 | 출처 |
|---|---:|---|
| 가로 | 20.00cm | **임의 지정** |
| 세로 · 두께 | 12.05cm · 7.79cm | 복원 비율로 계산, 실측 아님 |
| 무게 | 0.1kg | **임의 지정** (문서 허용 범위의 하한) |
| 가격 | 0 | 미확보 |
| 바코드 면 | -X 끝면 | 렌더 화면에서 사람이 판단 |

세로 치수는 특히 불확실하다. 가로·두께·윗면은 경계가 뚜렷하지만 밑면 쪽은 점 밀도가 서서히 줄어 경계가 흐리다. 복원 단위로 ±0.03, 세로의 약 ±7%로 본다.

## 시험에서 드러난 문제

자동 시험이 없었다면 놓쳤을 문제들이다. 앞의 두 건은 고쳤고, 나머지는 판단이 필요해 기록한다.

1. **고침 — 손이 상품을 감지하지 못함.** Starter Assets 근거리 캐스터의 물리 마스크가 `Default`뿐인데 상품은 `Interactable` 레이어에 있다. 샘플 프리팹은 그대로 두고 시험 씬의 리그 인스턴스에서 근거리 캐스터에만 `Interactable`을 추가했다. **`StoreScene`을 만들 때도 같은 설정이 필요하다.** 원거리 캐스터는 건드리지 않아 상품은 손으로 직접만 집힌다(5.1절).
2. **고침 — 시뮬레이터 마우스 기본값은 회전.** 수동 시험 때 `R`을 눌러야 이동 모드가 된다.
3. **판단 필요 — 고정 Attach는 쓸 수 없음.** 문서 5.2절의 "Attach Transform=무게중심"을 그대로 쓰면 앞면이 플레이어를 향한 상품이 집는 순간 180° 돈다. 지금은 Dynamic Attach로 집은 자세를 유지한다. 문서 개정 여부를 정해야 한다.
4. **판단 필요 — `side=+X`로 표현 불가.** 닭다리 바코드는 앞면 기준 오른쪽, 즉 -X 끝면이다. 4.4절 매핑으로는 나타낼 수 없어 `ProductData.BarcodeLocalNormal`을 추가했다. CSV 스키마는 바꾸지 않았다.
5. **판단 필요 — 레이어 매트릭스.** `Interactable × Scanner`가 켜져 있어 5.3절 주석과 다르다. `ScannerZone`이 태그로 걸러 판정은 정상이고, 몸통 진입이 스캔되지 않음을 시험했다. 매트릭스는 바꾸지 않았다.
6. **판단 필요 — `Player` 레이어 미등록.** 5.1절의 레이어가 TagManager에 없다. 얼굴 가까이 가져올 때 리그 캡슐에 막히지 않도록 지금은 `ProductPrefab`이 `Physics.IgnoreCollision`을 호출한다.

## 알려진 제한

- **밑면 결함.** [밑면 화면](evidence/dakdari_interaction/player/07_held_underside_known_defect.png)처럼 다른 면 내용이 겹치고 뾰족한 스플랫이 보인다. 상품을 뒤집는 순간 바로 드러난다.
- **아래쪽 잔상은 평소에도 보인다.** 작업대에 둔 상태에서도 앞면 아래 모서리에 어두운 잔상이 보이고([작업대에 눌렀을 때](evidence/dakdari_interaction/player/13b_pressed_on_bench.png)), [뒷면](evidence/dakdari_interaction/player/04_held_back.png) 아래쪽은 더 심하다. 3D 볼록껍질 분리로 바꿔도 줄지 않아, 분리 문제가 아니라 복원 모델 자체의 문제로 본다.
- **윗면 모서리 스파이크.** 바코드 끝면 쪽 윗면 모서리에 뾰족한 스플랫 무리가 있다([끝면](evidence/dakdari_interaction/player/03_held_barcode_end.png)).
- **바코드.** 줄무늬와 숫자 형태가 보이지만 실제 이미지 판독은 시험하지 않았다. 현재 스캔은 **충돌 판정 게임 규칙**이다.
- **작업대에 누를 때.** 이전에 약 2cm 파고든다고 보고했으나, 기울어짐까지 포함해 잰 잘못된 값이었다. 프록시 최저 모서리 기준으로는 약 0.6cm이고, 상품은 눌리면서 기운다. HMD에서 자연스러운지 봐야 한다.
- **자동 시험의 한계: 실제 마우스.** 시뮬레이터가 실제 마우스도 읽기 때문에, 실행 중 마우스를 움직이면 손이 같이 움직여 시험이 실패할 수 있다. 고래밥을 6회 반복했을 때 마우스가 움직인 1회(7,180단위)만 실패했고, 움직임이 없던 5회(0~1단위)는 모두 통과했다. 이 문제는 시험 환경의 영향이고 상품 결함이 아니다. 보고서의 `externalMouseMotion`에 이동량이 남으며, 최종 증거 6회는 모두 0이다. 시험 중에는 마우스를 건드리지 않는다.

## 실행 방법

씬: `Assets/Scenes/DakdariInteraction.unity`. 기존 `DakdariRefined` 씬과 에셋은 그대로다(SHA-256 동일 확인). 재생성은 메뉴 `Tools → P1 → Build Dakdari Interaction Trial`. 다른 상품은 [제작 과정 문서](상품_제작과정_시험_2026-11-07.md)의 재현 절차를 따른다.

| 입력 | 동작 |
|---|---|
| `Y` / `T` / `U` | 오른손 / 왼손 / 몸(시선) 조작 |
| `R` | 마우스 이동 ↔ 회전 전환 (시작은 회전) |
| 마우스 | 화면 평면 이동 |
| `Z` + 마우스 | 앞뒤 이동 |
| `Ctrl` + 마우스 | 회전 |
| `G` 누르고 있기 | 잡기, 떼면 놓기 |

순서: 시선을 아래로 → `Y` → `R` → 상품까지 손 이동 → `G` → `Ctrl`+마우스로 돌리기 → 바코드 끝면을 붉은 상자에 대기 → `G` 떼기.

자동 검증. Unity Hub가 실행 중이어야 라이선스를 찾는다. Hub가 꺼져 있으면 에디터가 종료 코드 198로 끝난다.

```powershell
& "C:\Program Files\Unity\Hub\Editor\6000.3.26f1\Editor\Unity.exe" -projectPath <프로젝트> -executeMethod P1InteractionTrial.VerifyEditor -p1-verify -p1-scene Assets/Scenes/DakdariInteraction.unity -logFile verify.log
```

```powershell
Builds\P1Interaction\P1Interaction.exe -p1-verify -p1-scene DakdariInteraction -p1-evidence <출력폴더> -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 -logFile player.log
```

인자 없이 실행하면 닭다리 씬 수동 조작 모드다. 다른 상품은 `-p1-scene GoraebapInteraction` 또는 `-p1-scene PotatoInteraction`을 붙인다. 이전 `Builds/P0Windows/P0Simulator.exe`는 이 씬을 포함하지 않는다.
