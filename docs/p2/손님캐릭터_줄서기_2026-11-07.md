# 손님 캐릭터·줄 서기·구경 손님 구현 (2026-11-07)

마일스톤 M2의 손님 부분이다(구현 문서 D4·D12, 6.1·6.2절, 마일스톤 P2-L4·P3-L1·P3-L3). 파란 캡슐이 입구에서 계산대까지 직선으로 오던 임시 손님을 사람 캐릭터와 NavMesh 이동으로 바꾸고, 11/07 Quest 2 리허설 소감("손님이 한 명씩 인위적으로 온다")으로 정한 줄 서기·구경 손님을 넣었다.

## 구현한 내용

### 손님 캐릭터 (D4)

- **에셋:** Microsoft Rocketbox 아바타 라이브러리(MIT, GitHub)에서 일상복 성인 4명을 사용자가 골랐다(남 `Male_Adult_08`·`Male_Adult_16`, 여 `Female_Adult_01`·`Female_Adult_17`). 반실사, 한 명당 7~9천 삼각형. 원본 키가 남 1.84m·여 1.77m라 0.95배로 줄였다. 원본 위치와 바꾼 점은 `Assets/ThirdParty/Rocketbox/README.md`에 있다(텍스처를 2048 TGA에서 1024 PNG로 줄임, 반사광·얼굴 표정 파일은 안 받음). 저장소는 2026-10-02에 읽기 전용으로 보관 처리됐다.
- **애니메이션:** D4의 3종을 Rocketbox 동작으로 채웠다. 대기 `idle_neutral_01`, 걷기 `walk_neutral_01`, 퇴장 `wave_01`(계산을 마치면 점원 쪽으로 손을 흔들고 나감, 최대 3초), 구경은 둘러보는 대기 `idle_look_around_01`. 남녀 동작을 따로 쓴다. 모두 Humanoid로 가져와 네 아바타가 같은 동작을 쓴다. 걷기는 에이전트 속도에 맞춰 재생 속도를 바꿔 발이 덜 미끄러지게 했다(측정은 안 함).
- **가져오기:** `P2CustomerSetup`(메뉴 `Tools > P2 > Setup Customer Characters`)가 텍스처·모델 설정, URP 재질(머리카락 카드는 알파 클리핑, 양면), 남녀 애니메이터, 아바타별 프리팹을 만든다. `P2StoreBuilder.Build`가 매번 부르고, 바뀐 것만 다시 가져온다.
- **레이어:** `Customer`(15번)를 추가했다. 환경(Default)과만 충돌하도록 설정했지만, 손님에게는 충돌체를 두지 않았다. 손님은 NavMesh로만 움직인다.

### 이동 (NavMesh)

- **패키지 없이 굽기:** 사용자 결정으로 AI Navigation 패키지를 넣지 않고, Unity 내장 AI 모듈의 `NavMeshBuilder`로 장면 빌더가 굽는다. `Packages/manifest.json`·`packages-lock.json`은 그대로다. 결과는 `Assets/Data/Navigation/StoreNavMesh.asset`이고 장면의 `StoreNavMesh`가 실행 시 올린다.
- **걸을 수 있는 곳:** 계산대 앞 손님 쪽 바닥과 출입문 현관뿐이다. 점원 구역에는 바닥을 주지 않아 손님 경로가 계산대 안쪽으로 나지 않는다. 벽·진열대·계산대는 모두 막는다. 에이전트 반지름 0.25m, 걷는 속도 1.1m/s.
- **빌드 때 검사:** 마커가 NavMesh 위에 있는지, 문에서 모든 마커까지 경로가 있는지, 점원 구역이 막혔는지를 굽자마자 확인하고 틀리면 빌드를 멈춘다. 매장 배치(P3-K1)가 오면 마커를 옮긴 뒤 이 검사가 먼저 잡아 준다.
- **서 있는 손님 피하기:** 처음에는 서 있는 손님도 에이전트로 두고 서로 피하게만 했다. 그러자 구경 손님이 줄 사이로 지나가려다 끼어 18초 만에 순간 이동했다(에디터 1회차, 아래 "작업 중 발견해 고친 것"). 지금은 멈춰 선 손님이 에이전트를 끄고 NavMesh에 구멍을 내는 장애물(카빙)이 된다. 걷는 손님의 경로는 처음부터 줄과 구경 손님을 돌아간다.
- **플레이어:** XR Origin에 `NavMeshObstacle`(카빙 끔)을 달고 `PlayerNavObstacle`이 몸통 캡슐을 따라가게 했다(구현 문서 5.1절). 손님과 플레이어 사이 물리 충돌은 없다.

## 실행 방법

에디터에서는 `Assets/Scenes/StoreScene.unity`를 열어 Play한다. 장면을 다시 만들려면 메뉴 `Tools > P2 > Build Store Scene`(캐릭터 설정도 같이 한다).

자동 검증(창이 뜨므로 마우스를 건드리지 않는다). 이 PC에는 Meta Horizon Link가 OpenXR 런타임으로 등록돼 있어, 검사할 때는 반드시 `XR_RUNTIME_JSON`을 없는 파일로 지정한다. 안 그러면 헤드셋에 게임이 뜨고 시뮬레이터가 꺼진다.

```powershell
$env:XR_RUNTIME_JSON = "C:\없는\파일.json"
Builds\Store\VRStore.exe -p2-verify -p2-evidence <출력폴더> -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 -logFile player.log
Builds\Store\VRStore.exe -p2-verify -customers-sequential -p2-evidence <출력폴더> -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 -logFile player.log
Remove-Item Env:\XR_RUNTIME_JSON
```

손님 캐릭터는 동시에 5~6명(한 명당 7~9천 삼각형 스킨 메시, 애니메이터, NavMesh 에이전트)이다. 데스크톱에서는 GPU가 거의 늘지 않았고 CPU가 약 0.2ms 늘었다. Link에서는 PC가 두 눈을 그리므로 캐릭터 그리기 비용이 데스크톱보다 크겠지만 측정하지 않았다. 손님이 없는 G1-H 장면(Mock 게이트)은 GPU 3.72/3.89ms로 기준선 3.73/3.99ms와 같다.

**느린 프레임과 3DGS 상품 생성.** 근무 중 20ms를 넘은 8프레임 중 6프레임이 손님이 계산대에 도착해 상품을 만드는 순간(0.15초 이내)에 있었고, 그중 4프레임은 GPU가 42~49ms였다. 나머지 2프레임(34.7ms, GPU 약 2ms)은 손님 일과 겹치지 않았다. 손님 캐릭터 등장(이 실행에서 19회)과 겹친 느린 프레임은 없었다. 측정기 시각과 손님 기록은 시계가 달라, 가장 많은 프레임을 맞추는 오프셋(2.68초)을 찾아 맞췄다. 마우스가 섞여 다시 돌린 앞 실행에서도 같은 오프셋 근처(2.74초)에서 9프레임 중 7프레임이 맞았다. Quest 2 리허설의 "40~60초마다 27~42ms" 프레임이 상품 생성 때문이라는 추정을 뒷받침하지만, 시각을 맞춘 것이지 원인을 직접 잡은 것은 아니다. D12대로 상품은 도착 때 만들므로 이번 작업으로 생긴 문제는 아니다. 줄에서 기다리는 동안 다음 주문의 상품 자원을 미리 준비하는 식의 개선은 후속 과제로 남긴다.

- 동작 FBX를 처음 가져올 때 `Rig Error: Copied Avatar Rig Configuration mis-match`가 로그에 나온다. 허벅지 뼈 위치가 4.5~20mm 다르다는 뜻이고 동작에는 문제가 보이지 않았다. 설정이 바뀌지 않으면 다시 나오지 않는다
- 빌드는 `ProjectSettings/TagManager.asset`(15번 `Customer` 레이어)과 `DynamicsManager.asset`(충돌 행렬)을 고친다

## 작업 중 발견해 고친 것

- **줄 사이에 끼인 구경 손님.** 에디터 1회차에서 구경 손님 한 명이 선반 A로 가다가 계산대 앞 손님과 줄 첫째 사이(틈 약 0.3m)를 지나려다 18.4초 동안 갇혀 순간 이동했다(`customers.no_stuck_walks` 실패, 194개 중 1개). NavMesh가 서 있는 손님을 모르니 경로가 줄 한가운데로 났고 국소 회피로는 빠져나오지 못했다. 위의 카빙 방식으로 바꾼 뒤 모든 실행에서 0회다. 이 실행에는 실제 마우스 입력(2067)도 섞여 결과 전체를 다시 돌렸다.
- **문 앞에서 서로 비켜 주다 멈춘 손님.** 메인 플레이어의 걷기 포함 검사에서 구경 손님 둘과 계산을 마친 손님이 거의 동시에 같은 문 지점으로 갔고, 한 명이 그 점 0.25m 앞에서 13.5초 막혀 순간 이동했다(207개 중 1개 실패). 문 지점만 여러 명이 함께 쓰는 목적지였다. 나가는 손님은 이제 문 지점 0.6m 안(어두운 현관 안)에 들어서면 사라진다. 구경 지점·줄 자리·계산대는 원래 한 명씩만 쓴다.
- **줄이 당겨질 때 목적지 앞에서 멈출 수 있던 경로.** 앞사람이 아직 장애물(구멍)을 거두기 전에 경로를 계산하면 목적지 바로 앞에서 끝난다. 정해진 자리로 가는 걸음이 0.2m 넘게 모자라면 경로를 다시 잡게 하고, 줄을 당길 때는 0.4초 뒤에 움직이게 했다(사람이 알아채는 시간). 모자란 채 끝난 걸음 수를 `customers.reached_exact_spots`로 검사한다(최종 0회). 실제로 모자랐던 경우를 본 것은 아니고 코드를 읽다 찾은 가능성이다.
- **구경하다 불려 간 손님의 대기 동작.** 진열대를 보다 불려 가면 계산대 앞에서 돌아서는 동안 둘러보기 동작이 잠깐 섞일 수 있었다. 부르는 순간 대기 동작으로 바꿨다.
- **바구니가 A자세 손에 붙음.** 생성 직후에는 골격이 모델의 A자세라 손 방향이 대기 동작과 달랐다. 대기 동작을 한 번 평가한 뒤 붙이게 했다(스크린샷으로 똑바로 든 것 확인).
- **검사 실행 2회에 실제 마우스 입력이 섞임.** 에디터 1회차(2067)와 메인 성능 측정 1회차(544, `input.set_downs_were_still` 실패)다. 두 회차 모두 다시 돌렸고 표의 결과는 마우스 0인 실행만이다.
