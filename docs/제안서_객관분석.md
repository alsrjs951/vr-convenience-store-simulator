- **분석 대상**: `VR_편의점_알바_시뮬레이터_제안서.pptx` (15장) / 추출 원문 `docs/제안서_원문.md` (355줄)
- **분석 방법**: 4개 관점(기술실현성·요구사항완전성·게임디자인·일정리스크)의 평가 결과 39건을 원문과 대조해 인용을 전수 확인했고, 방향을 바꿀 수 있는 외부 사실 4건(UnityGaussianSplatting README·이슈 #145·Worldlabs 호환 문서·nerfstudio 공식 문서)을 이번 분석 중 직접 재확인했다. 인용이 원문에 없어 제외된 항목은 없었고, 중복 7건은 통합했다.
- **질의응답(2026-10-24)**: 6개 결정 질문에 사용자 응답이 없어(미응답) 종합 분석가의 권장안을 **기본값**으로 채택했다(전 항목 '사용자 확인 필요' 상태). 결정 내용은 §5 '확정된 결정 사항' 표에 모았고, 개선 권고 1·2·3·4·5·6·9번에 반영했다.
- **하드 제약 전제**: 3D 렌더링 + HMD VR + NeRF/가우시안 스플래팅 사용은 확정된 전제로, '쓸지 여부'는 이 분석의 대상이 아니다.

## 1. 개요 — 제안 요약

권도훈·이민건 2인팀이 2026년 2학기 가상현실 Term Project로 6주(2026/10/14~11/24)간 제작할 VR 편의점 알바 시뮬레이터의 기획서다.

- **핵심 차별점**: 만화풍 3D 모델 대신 실제 편의점 상품을 스마트폰으로 촬영해 3D 가우시안 스플래팅(3DGS)으로 복원하고, 상품을 4겹(스플랫·프록시 콜라이더·바코드 트리거·상품 데이터)으로 구성해 "상품 1종 추가 = 촬영 + 상품 표(CSV) 한 줄" 확장성을 주장한다(슬라이드 4·7, 원문 86-88·154).
- **기술 스택**: Unity 6.3 LTS(URP) + OpenXR/XR Interaction Toolkit + UnityGaussianSplatting(MIT). 3DGS 생성은 Scaniverse / nerfstudio splatfacto, NeRF(nerfacto) 비교 실험 계획(슬라이드 6, 원문 139-144). VR 빌드는 Windows + DX12.
- **플레이**: 손님 주문 → 계산(바코드 스캔) → 봉투·결제 → 진열·폐기 → 정산의 하루 근무 루프를 3일차까지 확장(1일차 튜토리얼·손님 5명 → 3일차 피크타임·전자레인지·컵라면 물)(슬라이드 12, 원문 267-275).
- **목표 수치**: 실사 상품 20종+(MVP), 플레이 분량 10~15분, HMD 72fps+(슬라이드 4·5, 원문 90·114).
- **마일스톤**: 11/3 MVP → 11/10 알파(3일차까지) → 11/24 최종 발표. 역할은 권도훈(3DGS 캡처·콘텐츠) / 이민건(VR 인터랙션·시스템)이 상품 표를 매개로 연결(슬라이드 10·14, 원문 222-227·317-337).

## 2. 강점

1. **리스크 우선 스케줄링** — 최대 기술 불확실성(광택 있는 페트병·캔의 스캔 가능성, 3DGS의 VR 렌더링)을 1주차에 배치하고 Go/No-go 마일스톤으로 조기 판정하는 구조는 교과서적이다(슬라이드 10, 원문 222). 4개 관점 평가 모두 이 점을 강점으로 독립 확인했다.
2. **기술 제약의 정확한 인식** — "Windows에서 3DGS 렌더더는 DX12 또는 Vulkan이 필요 (DX11 미지원)" 주석(슬라이드 6, 원문 147)은 업스트림 README("DX11 will not work")와 정확히 일치함을 이번 분석에서 재확인했다. "3DGS에는 메시와 충돌 정보가 없다 → 외형(스플랫)과 물리(박스 콜라이더)를 별도 레이어로 분리"(슬라이드 8, 원문 193)도 실제 제약에 대한 정확한 대응이다. Unity 6+URP 스택도 공식 지원 경로다.
3. **기술 제약을 게임 규칙으로 전환** — "바코드 찾기가 곧 게임 규칙"(슬라이드 8, 원문 197): 바코드 면에만 트리거를 두어 상품을 돌려 찾아야 인식되는 설계는, 3DGS의 한계를 플레이 행동으로 바꾼 문서에서 가장 강한 게임디자인 결정이다.
4. **데이터 중심 확장 설계** — 상품 표(CSV) + 자동 프리팹(크기 맞춤·콜라이더·바코드 트리거 부착) 파이프라인(슬라이드 7, 원문 158-175)과 "상품 표 + 정제 PLY → 자동 프리팹"으로 2인 역할을 연결한 구조(슬라이드 14, 원문 335)는 2인팀 규모에 맞는 명확한 인터페이스다.
5. **진열대 렌더링 최적화의 단계화** — 측정 → 병합 → 분리 → 경량화의 4단계 계획(슬라이드 9, 원문 206-211)은 VR 스플랫 렌더링의 알려진 병목을 의식한 구체적 대응이다. 다만 실효성의 한계는 §3-A에서 별도로 다룬다.
6. **VR 멀미를 비기능 요구사항으로 명시** — "텔레포트·고정 위치로 멀미 최소화"(슬라이드 5, 원문 116). VR 제안서에서 자주 빠지는 항목을 요구사항 수준에서 다뤘다. (단, 핵심 루프와의 모순은 §3-I 참조.)

## 3. 약점·리스크

### A. [높음] 유일한 렌더링 기반의 성숙도·호환 리스크가 문서에서 사라져 있다

- **"개발 중단된 토이 프로젝트 + 조건부 VR 지원"을 무조건 지원으로 서술** — 슬라이드 6은 "UnityGaussianSplatting (MIT, VR 지원)"이라고 쓰나(원문 141), README 원문은 "⚠️ Status as of 2023 December: I'm not planning any significant further developments"이며 VR은 "Some virtual reality devices work (reportedly HTC Vive, Varjo Aero, Quest 3 and Quest Pro). Some others might not"라는 제보 수준이다(이번 분석 재확인). 2023년 12월 이후 개발 중단 선언된 렌더러 위에 프로젝트 전체가 서 있으므로, 발견되는 버그를 상류에 기대해 고칠 수 없다.
- **Unity 6.3 + VR 조합의 미동작 보고** — 제안서는 "Unity 6.3 LTS (URP)"(슬라이드 6, 원문 139)를 명시하나, 외부 가이드(Worldlabs)는 "The aras-p plugin does not work for VR on Unity 6.3. Use Unity 6.0 (6000.0.23f1)"이라고 안내한다(이번 분석 재확인). 단일 비공식 소스이므로 확정 사실은 아니나, 1주차 게이트에서 버전 호환까지 확인할 충분한 이유다.
- **72fps+ 목표 vs 검증된 최악 시나리오(근접 오버드로)** — 슬라이드 5 "HMD에서 72fps 이상 유지"(원문 114), 슬라이드 4 "72fps+ HMD 프레임 목표"(원문 90). 업스트림 이슈 #145는 VR에서 "72fps에서 최저 10fps까지" 급락하는 사례를 보고하며 — 15만~17.5만 스플릿(소량)에서도 발생 — 원인은 스플릿 수·정렬이 아니라 화면을 덮는 큰 스플릿의 프래그먼트 셰이더 부담이고, "not planned"로 종료됐다(이번 분석 재확인). 슬라이드 9의 2단계 Merge는 스플릿 수만 줄일 뿐 화면 커버리지(오버드로)는 줄이지 않으므로 이 결함의 근본 원인에 작동하지 않을 수 있다. 4단계 '원거리 경량화'도 슬라이드 12의 소형 매장(냉장고+진열대 A/B/C+계산대, 원문 265)에서는 적용 폭이 좁다. 이슈에서 실제 보고된 완화책(렌더 해상도 조정, 알파 컬링 임계값, FSR)은 제안서에 없고, 스플랫 수 예산·해상도 전략도 문서 어디에도 없다.
- **렌더러 공식 제약 vs 핵심 설계·필수 기능의 충돌 미검토** — 공식 문서는 다중 GaussianSplatRenderer의 "heavy overlap can produce incorrect results"(위치 기반 대략 정렬), MSAA 미지원, 무조명(no lights/shadows/reflection probes), 일반 반투명 오브젝트와 "don't blend well"을 명시한다. 그런데 이 게임의 핵심 프레임은 '손에 든 개별 스플릿 렌더러 + 병합 진열대 렌더러'가 화면에서 겹치는 장면(슬라이드 9 3단계, 원문 210)이고, 필수 기능에 '비닐봉투 담기'(반투명 메시와의 블렌딩, 슬라이드 5, 원문 105), 차별점에 '비닐 광택' 재현(슬라이드 4, 원문 87)이 있다. 제안서는 이 충돌을 다루지 않는다.
- **최적화 시점 지연** — 진열대 최적화(병합·경량화)가 전부 5주차(슬라이드 10, 원문 226)에 몰려 있어, 슬라이드 9 1단계 "먼저 HMD 프레임을 측정한다"(원문 208)와 상충한다. 72fps 검증이 최종 발표 2주 전으로 밀린다.

### B. [높음] 성공 판정 기준이 없어 Go/No-go가 이름뿐인 게이트다

- 1주차 게이트(10/20, 이미 경과)는 "페트병·캔 스캔 가능 여부 판정", "3DGS VR 렌더링 검증"(슬라이드 10, 원문 222)만 있고, '가능'을 무엇으로 판정하는지(스캔 품질 수치, 프레임 기준, 소요 시간 상한)가 문서 전체에 없다. No-go일 때의 플랜 B(메시 폴백, 광택 없는 상품으로 한정, 기기 축소)도 없다.
- 핵심 목표 '실재감'은 "평가하기 좋다"(슬라이드 3, 원문 65)와 "실측 크기 반영"(슬라이드 5, 원문 115)뿐이고, FPS·품질은 "측정한다"(슬라이드 10·14, 원문 226·322)는 활동만 있을 뿐 측정 도구(설문·프레즌스 척도·Profiler·샘플링 조건)와 합계 임계값이 한 곳도 없다. 목표와 측정의 단결.
- **타깃 HMD 기종·연결 방식이 전 문서에 없다** — "HMD"는 항상 일반 명칭으로만 등장한다(슬라이드 4·5·6·14, 원문 90·114·144·333). 기종(Quest 3? Vive?)과 연결(PCVR vs 스탠드얼론)에 따라 72fps의 실현 난이도와 렌더러 호환("reportedly" 목록)이 완전히 달라지며, Windows PC의 GPU 사양(최소 사양)도 명시돼 있지 않아 나중에 '노트북으로는 안 나온다'식의 판정 기준 논쟁이 예상된다.

### C. [높음] 3DGS 학습 인프라 공백 — splatfacto는 CUDA(NVIDIA GPU) 필수인데 학습 머신이 macOS

- 슬라이드 6은 생성 경로로 "스마트폰 촬영 → Scaniverse / nerfstudio splatfacto"를 두고(원문 142), 개발 PC는 "macOS (3DGS 에셋) · Windows + DX12 (VR 빌드)"(원문 144)로 배정했다. 그러나 nerfstudio 공식 문서는 "Nerfstudio uses gsplat as its gaussian rasterization backend … The associated CUDA code will be compiled"(이번 분석 재확인)로 gsplat CUDA 커널 의존을 명시하고, nerfstudio maintainer는 "Splatfacto requires CUDA for training right now"라고 답해왔다(이슈 #3290). CUDA는 사실상 NVIDIA GPU를 요구하므로 Apple Silicon macOS에서 학습이 불가능하다.
- 학습 담당(3DGS 리드)의 캡처 업무가 "촬영 환경 구축, 상품 촬영 · 학습, 배경 · 떠다니는 점 정제"(슬라이드 14, 원문 321)로 명시돼 있어 모순이다. Windows 기기가 NVIDIA GPU를 갖는지도 미상이다(DX12는 그래픽 API지 GPU 벤더가 아니다). Scaniverse는 폰에서 완결되므로 우회 가능하지만, 제안서는 두 경로의 이 구분을 언급하지 않아 '페트병·캔 등 반사 재질에서 Scaniverse 품질이 부족할 때'(정확히 1주차 게이트가 묻는 지점) 학습 수단이 계획서에 존재하지 않는다.

### D. [높음] 필수 기능 '손님'의 구현 계획이 전무하고, 3일차 곡선은 '확장' 기능 위에 서 있다

- **손님 NPC 계획 부재** — "근무 흐름 | 손님 주문 → 계산 → 하루 정산 | 필수"(슬라이드 5, 원문 106), "1일차 … 손님 5명"(슬라이드 12, 원문 273)인데, 사람 캐릭터의 3D 모델 조달·애니메이션·경로 이동·대사/음성 계획은 슬라이드 14 분담내역 어디에도 없다(이민건 역할에도 "매장 3D 제작"만 있음). 상품에는 6단계 파이프라인(슬라이드 7)이 있는데 사람 캐릭터 제작 경로는 없어 공수 산정 자체가 불가능하다. 목업(슬라이드 11)에도 손님은 없고 주문 HUD만 있다.
- **피크타임 재미 설계 부재** — 손님의 표현 수단(비주얼·음성·대기열)과 피크타임의 압박 피드백(인내심 게이지·점수·콤보·오디오) 설계가 없어 '3일차 피크 타임'은 손님 수 증가 이상의 재미로 성립하지 않는다. 피크타임 난이도 파라미터(손님 수·스폰 주기·제한시간·실패 조건)는 문서 어디에도 없고 유일한 수치는 1일차 '손님 5명'뿐이다.
- **곡선의 2/3가 확장 분류 기능에 의존** — 2일차 진열·폐기, 3일차 피크타임·1+1·전자레인지·컵라면 물(슬라이드 12, 원문 274-275)은 요구사항 표에서 모두 '확장' 우선순위다(슬라이드 5, 원문 107-108). 확장 기능이 잘리면 곡선 전체가 붕괴한다. 그런데도 4주차 알파에 확장 기능 전부가 확정 투입돼 있고(슬라이드 10, 원문 225), 'MVP가 X일 지연하면 특수 요청을 3일차에서 제외한다' 같은 디스코프 트리거와, 신규 기능 종료→기능 동결(5주차) 사이 버퍼가 0주라는 문제가 있다. 상품 수도 "20종+"로 상한 없이 개방형이다(슬라이드 4, 원문 90).

### E. [높음] 일정 밀도와 단일 인력 의존 — 그리고 이미 경과한 시간

- **1/4 경과, 기록 없음** — 오늘(2026-10-24)은 2주차(10/21~10/27) 한가운데다. 1주차 게이트(10/20)의 결과 기록이나 현재 시점 재계획(베이스라인 재설정)이 15장 전체에 없어 이 계획대로 진행 가능한지 판단할 출발점 자체가 없다(슬라이드 10, 원문 222-223).
- **3주차 MVP의 밀도** — 상품 수 2배 증가(10→20종)와 계산대(봉투·결제)·1일차 근무 흐름, 즉 게임 핵심 시스템 전부를 7일 안에 끝내야 한다(슬라이드 10, 원문 224). 직전 2주차 팀원 산출물은 "잡기 · 바코드 판정, 자동 프리팹 도구"(원문 223)뿐이라 2→3주차 사이에 '잡기'에서 'MVP 플레이'로 도약해야 한다. 결제 UI·거스름돈·정산·손님 5명 처리가 전부 이 한 주다(슬라이드 5·12).
- **4주차 알파의 밀도** — 확장 기능 3종(진열·폐기·특수 요청)과 손님 시스템, 그리고 이 시점에 처음 등장하는 '매장 3D 제작'(3주차는 "매장 레이아웃 설계"뿐)까지 전부 팀원 1인의 한 주에 몰려 있다(슬라이드 10·14, 원문 225·331-333). 3주차 MVP가 하루만 밀려도 알파가 성립하지 않는 구조다.
- **캡처 파이프라인 1인 전담 + 시간 예산 부재** — 촬영→학습→수동 정제(배경 컷아웃·플로터 제거) 전 과정이 팀장 1인 몫이고(슬라이드 7·14, 원문 160-162·321), 시험 스캔 3종(1주) → 10종(2주) → 20종(3주)의 램프가 가파르다(슬라이드 10). 상품당 처리 시간 추정이 문서에 전혀 없어(정제는 상품당 수십 분~수 시간의 수작업이 될 수 있다), 스캔 품질 편차·재촬영이 일정을 잠식할 여지가 크다. 품질 문제로 재촬영이 반복되면 대체 인력이 없어 MVP·알파 일정에 직격이다.

### F. [보통] "상품 표 한 줄" 확장성 주장이 자기 파이프라인과 모순된다

- "상품 1종 추가 = 촬영 + 상품 표 한 줄"(슬라이드 4·7, 원문 88·154), "상품 표 한 줄 추가 = 상품 추가"(슬라이드 5, 원문 117)라는 핵심 주장은, 같은 파이프라인의 STEP 3 수동 정제(원문 162)와 슬라이드 9의 진열대 Merge(신규 상품마다 해당 칸 재병합 필요, 병합본+개별본 2벌 유지, 원문 209)라는 반복 수작업을 빼고 있다. Invert 컷아웃(원문 210)은 실제 존재하는 기능이지만 볼륨 경계에 일부만 걸치는 가우시안 처리(밀집 진열대에서 인접 상품을 베거나 잔여 꼬리를 남길 수 있음)는 문서화돼 있지 않아 실험 없이는 동작 가정이다.

### G. [보통] '인쇄 글씨까지 사진처럼 재현'은 3DGS의 문서화된 약점과 정면충돌한다

- 슬라이드 4(원문 87)의 이 약속은 3DGS가 고주파 디테일(선명한 텍스트)을 균일 처리로 손실시킨다는 알려진 특성 및 스마트폰 촬영의 모션/초점 블러가 재구성으로 전파된다는 연구 결과와 충돌한다. 매일 보는 상품의 글씨 흐림은 '진짜 같은지' 목표에서 가장 먼저 들통나는 지점인데, 완화책(해상도 상향, 바코드·라벨 면만 실사 텍스처 혼합 등)이 없다.

### H. [높음] 실제 브랜드 상품 재현의 저작권·상표·라이선스 문제가 전무하다

- "실제 상품을 … 촬영해", "인쇄 글씨까지 사진처럼 재현"(슬라이드 4, 원문 86-87)하면서 "아르바이트 사전 교육 콘텐츠로 활용 가능"(슬라이드 13, 원문 300)까지 서술하는데, 상표·저작물 재현에 대한 허위 없는 대응(허가, 가상 브랜드 라벨 대체, 범위 한정)이 한 줄도 없다. 도구 체인 라이선스도 "(MIT, VR 지원)"(슬라이드 6, 원문 141)으로 과단순화돼 있는데, README는 "commercial usage requires getting license from INRIA"라고 경고한다(이번 분석 재확인 — 교내 과제 범위인지, 외부 활용 전망(슬라이드 13)까지 가는지에 따라 요건이 달라진다).

### I. [보통] 플레이 경험 관련 명세 공백 (사운드·현금·튜토리얼·페이싱·멀미·접근성)

- **사운드 전무** — 전 문서에서 오디오는 스캔 효과음 '삑' 암시(슬라이드 8·11, 원문 197·242)뿐이고, 매장 환경음·손님 음성·결제 단말기 소리 등 실재감 직결 요소의 계획·분담이 없다.
- **현금·거스름돈 물리 방식 불명** — "카드·현금 결제와 거스름돈 계산 | 필수"(슬라이드 5, 원문 105)인데 지폐·동전을 물리적으로 조작하는 방식의 명세가 없다. 주문 HUD(슬라이드 11, 원문 239)의 월드 스페이스 여부·가독성 기준, 왼손잡이·키 조절·자막 등 접근성도 멀미 최소화 하나뿐이다.
- **페이싱 정합성** — "10~15분 3일차 근무 플레이 분량"(슬라이드 4, 원문 90)과 목업의 주문 타이머 "02:30"(슬라이드 11, 원문 249) 사이 검토가 없고, 일차 종료 조건(손님 수? 시간? 과제 완료?)이 정의되지 않아(슬라이드 12, 원문 267) 분량 목표를 설계로 검증할 수 없다.
- **튜토리얼 설계** — "1일차 튜토리얼 · 계산만, 손님 5명"(슬라이드 12, 원문 273) 한 줄뿐이다. 가르쳐야 할 조작 체인(잡기→회전→바코드 탐색→스캔→봉투→카드/현금+거스름돈)은 6단계 이상인데 단계별 안내·실패 회복·VR 초심자 배려가 전무하다.
- **멀미 대책 vs 핵심 루프 모순** — 고정 위치·텔레포트로 멀미를 최소화한다면서 핵심 루프는 계산대⇄진열대 왕복(슬라이드 12, 원문 267)이고, 집는 순간의 스플랫 교체(병합 진열대→개별 스플랫) 팝(슬라이드 9, 원문 210)과 20종+ 스플랫 로딩 전략 등 몰입 킬러 대응이 없다.
- **출처 없는 핵심 수치·주장** — '검증된 VR 소재'(Job Simulator 근거, 슬라이드 4, 원문 81), 20종/10~15분/72fps 목표의 산출 근거(슬라이드 4, 원문 90), 교육 효과 주장(슬라이드 13)에 인용·측정 근거가 전무하다(문서에 참고자료 섹션 자체가 없음).

### J. [낮음] 파이프라인 표기 불일치

- STEP 1은 "사진 촬영"(원문 160), STEP 2는 "영상 → 가우시안 (PLY / SPZ)"(원문 161)으로 입력이 사진인지 영상인지 불일치한다. SPZ는 사실상 Scaniverse 출력 포맷이고 splatfacto 출력은 PLY이므로 "splatfacto → PLY/SPZ" 병기는 출처가 섞여 있다. 정제 단계(배경·플로터 제거)에 쓸 도구(SuperSplat, 에디터 내 splat editing 등)도 미지정이다.

## 4. 개선 권고

1. **일정 재베이스 — D1 기본값 채택** — 게이트 결과 기록이 없는 것으로 간주하고(사용자 미응답) 오늘(2026-10-24) 이후를 기준으로 주 단위 일정을 다시 짠다. 게이트(스캔 3종 품질 판정 + VR 프레임 측정)를 재계획 1주차에 다시 배치한다. 원 게이트 기한(10/20)은 이미 경과했다.
2. **Go/No-go 판정 기준 수치화 + 플랜 B** — 예: "스캔 3종 모두 인쇄 글씨 판독 가능 + 정제 포함 상품당 X시간 이내", "대표 장면(진열대 근접)에서 72fps", 스플랫 수 예산(상품당/장면당). No-go 시 플랜 B(메시 폴백, 광택 없는 상품 한정, 렌더 해상도 축소·알파 컬링·FSR — 이슈 #145에서 실제 보고된 완화책)을 미리 적어둔다. 이 기준은 D1 재베이스 일정의 게이트에 그대로 적용한다.
3. **HMD 기준 확정 — D2 기본값 채택** — Quest 3 + Link/PCVR로 정하고, 72fps 측정 기준을 'Link 대상 Windows PC의 GPU 사양'으로 문서에 명시한다(§3-B의 '기종·측정 기준 부유' 해소). 스탠드얼론(Quest APK)은 배제하며 이슈 #145의 Android 랙 사례는 참고 자료로만 남긴다. Unity 6.3에서 VR 미동작 보고가 있으므로 6.0(6000.0.23f1 계열) 폴백 준비·재베이스된 게이트에서의 함께 검증은 유지한다(§3-A). **→ 2026-11-06 답변으로 목표 기종은 Meta Quest 2(+ 유선 Link/PCVR)로 확정(질의응답 참조).**
4. **학습 경로 2단계화 — D3 기본값 채택** — 1차 Scaniverse(폰에서 완결), 반사 재질(페트병·캔)에서 품질이 부족할 때 Windows PC의 NVIDIA GPU로 splatfacto 학습. NVIDIA GPU가 확보되지 않을 경우의 플랜 B(Scaniverse 단일 경로 + splatfacto는 Colab)도 문서에 함께 둔다. 이로써 §3-C의 'macOS 배정 vs CUDA 필수' 모순은 해소되고, 개발 환경 표(슬라이드 6)의 'macOS (3DGS 에셋)' 배정 수정과 정제 도구(SuperSplat 등) 지정이 과제로 남는다.
5. **손님 표현 확정 — D4 기본값 채택 + 분담 배정** — 사람 캐릭터 없이 주문 HUD·바구니·음성 중심으로 확정(슬라이드 11 목업과 부합). 저폴리 캡슐 캐릭터는 일정 여유가 생겼을 때의 확장 옵션으로만 기록한다. 남은 과제: 바구니·음성·주문 HUD 시스템을 슬라이드 14 분담내역에 배정해 공수를 산정 가능하게 하고, 피크타임 파라미터(손님 수·스폰 주기·실패 조건)를 최소한으로 정의한다(§3-D 해소 경로 확정). **→ 2026-10-25 답변으로 반전: 캐릭터 도입 확정(질의응답 참조).**
6. **디스코프 규칙 확정 — D5 기본값 채택** — 상품 수 상한 15종(슬라이드 4 "20종+" 및 슬라이드 10 3주차 "상품 20종 완료"도 15종 기준으로 수정 필요). 트리거 2건을 문서화한다: "3주 MVP가 3일 이상 지연되면 특수 요청을 3일차에서 제외", "재촬영 2회 초과 상품은 목록에서 뺀다". 이로 '확장' 라벨이 실제 스코프 관리 장치로 작동하고, 4주차 팀원 1인 몰집 분산은 과제로 남는다(§3-D·E). **→ 2026-10-25 답변으로 변경: 상한 폐지·계속 추가, 관리는 스플랫 예산과 재촬영 상한(질의응답 참조).**
7. **캡처 파이프라인의 시간 예산 측정·분산** — 상품당 촬영·학습·정제 시간을 실측해 20종 램프(3종→10종→20종)의 근거로 삼고, 촬영·정제 일부를 팀원과 분담하거나 재촬영 버퍼를 상한과 연동한다.
8. **"표 한 줄" 주장을 실제 워크플로에 맞게 수정** — 정제·재병합 포함의 실제 확장 절차로 고쳐 쓰거나, 해당 단계의 자동화 범위를 명시한다. Invert 컷아웃 경계 품질은 1~2주차에 작은 실험으로 검증한다.
9. **IP·라이선스 문구 확정 — D6 기본값 채택** — ① 본 재현은 교내 과제 한정임을 문서에 명시, ② 외부 공개·활용 시 가상 브랜드 라벨로 교체하는 계획을 각주로 남긴다, ③ 3DGS 렌더러(가우시안 래스터화)의 INRIA 상업 라이선스 요건을 함께 명시한다(§3-H 해소). **→ 2026-10-25 답변으로 확정: 외부 비공개·실제 상품 사용(질의응답 참조).**
10. **최소 명세 보강** — 오디오(환경음·효과음), 현금·거스름돈 조작 방식, HUD 가독성, 튜토리얼 단계, 일차 종료 조건, 핵심 수치의 출처. 모두 '완성 목록'이 아니라 판정 가능한 한 줄씩이면 충분하다.

### 질문-답변 상세와 분석·권고에 미치는 영향

**Q1. 1주차 Go/No-go 게이트(10/20) 결과와 현재 진행 상태는?**
- 답변(확정 2026-10-25): 스캔 테스트는 아직 못 했다. 일정은 구체적 날짜 없이 순서 중심으로 다시 잡는다. **3차 답변(2026-11-06): 발표가 11월 17일로 앞당겨졌다.**
- 분석·권고 변화: 권고 1이 '재베이스'에서 '순서 기반 재계획'으로 확정됐다. §3-E의 '1/4 경과·기록 없음' 약점 자체는 제안서에 대한 기술이므로 유지되지만, 해소 경로가 확정됐다.
- 3차 답변의 영향(2026-11-06): 남은 기간이 11일(11/06~11/16)로 줄어 §3-E의 '일정 밀도' 약점이 다시 가장 큰 리스크가 됐다. 권고 1은 '순서 기반 재계획'에서 '발표일 역산 날짜 계획 + 날짜 기반 디스코프 트리거(T1 11/12 · T3 11/14)'로 바뀌었고, NeRF·3DGS 비교 학습을 11/09부터 백그라운드로 당겨 마지막 주 몰림을 줄였다(구현 문서 8장).

**Q2. 타깃 HMD 기종과 연결 방식은?**
- 답변(확정 2026-10-25): VR 기기는 대여할 수 있을지 불명확하다 — 대여할 수 없음을 기본값으로 한다. (목표 기종·연결 방식은 Quest 3 + Link/PCVR 유지.) **3차 답변(2026-11-06): HMD 기기는 Meta Quest 2로 확정됐고, 기기는 이미 확보했다.**
- 분석·권고 변화: 권고 3이 '기기 확보 여부와 무관하게 진행되는 작업 / 기기 확보 시 검증'의 2분 구조로 확정됐다. §3-A·B의 실기기 성능 리스크(72fps·렌더러 VR 지원)는 '기기 확보 전까지 미측정 리스크'로 남고, 시뮬레이터·에디터 개발 경로가 주경로가 됐다.
- 3차 답변의 영향(2026-11-06): §3-B의 '기종 부유'가 완전히 해소됐다. Quest 2는 Quest 3보다 패널 해상도가 낮아 같은 장면의 렌더 부하는 줄지만 라벨 판독성이 떨어지므로, 게이트의 라벨 판독(G1-a)은 Quest 2 착용으로 확정한다(구현 문서 2.7절). 기기는 같은 날 이미 확보했다고 확인돼 3중 확보 경로는 비상용으로만 남는다.

**Q3. splatfacto 학습에 쓸 수 있는 NVIDIA GPU가 있나?**
- 답변(확정 2026-10-25): 집 데스크톱이 Windows + RTX 4070이다 — 맥북에서 원격 연결해 GPU 컴퓨팅 파워를 빌려 쓴다.
- 분석·권고 변화: 권고 4의 '학습 인프라 확보'가 완전 해소됐다(§3-C 모순 종결). 개발 환경 표(슬라이드 6)의 'macOS (3DGS 에셋)'는 정제·데이터 관리로, 학습은 RTX 4070 원격으로 수정 반영된다.

**Q4. 손님 NPC 표현 수준은?**
- 답변(확정 2026-10-25): 손님은 캐릭터를 만들면 좋겠다.
- 분석·권고 변화: 권고 5가 '캐릭터 도입(에셋 기반 최소)'으로 확정됐다 — §3-D의 '캐릭터 제작 계획 부재'를 회피가 아니라 도입으로 해소하되, 2인 팀 공수 보호를 위해 커스텀 제작 없는 에셋·최소 애니메이션 경로를 구현 문서가 규정한다.

**Q5. 상품 수 상한과 디스코프 트리거는?**
- 답변(확정 2026-10-25): 상품은 우선 계속 추가한다(상한 없음).
- 분석·권고 변화: 권고 6의 '상한 15종'은 폐지됐다 — 스코프 관리는 스플랫 수 예산(성능 상한)과 재촬영 상한(품질 상한)이 대신한다. 'MVP 지연 시 특수 요청 제외' 트리거는 날짜 없는 순서 규칙(MVP 완료 후 착수)으로 수정 반영됐다.

**Q6. 실제 브랜드 상품 재현의 IP·라이선스 범위는?**
- 답변(확정 2026-10-25): 외부에 공개할 프로젝트가 아니므로 실제 상품을 찍어도 괜찮다.
- 분석·권고 변화: 권고 9가 '실제 상품 사용 확정(외부 비공개)'으로 해소됐다. 가상 라벨 교체·INRIA 상업 라이선스 요건은 전환 시에만 검토하는 각주로 남는다(§3-H 마무리).
